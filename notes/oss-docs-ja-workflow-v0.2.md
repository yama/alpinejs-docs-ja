# OSS公式ドキュメント日本語化 標準ワークフロー v0.2

## この文書の位置づけ

この手順は、OSS公式ドキュメントを日本語化するときに、人間とAIが同じ順序で作業し、AIが安全に作業を継続するための実務手順です。

v0.1の基本設計を維持し、Livewire日本語版とAlpine.js日本語版で得られた実証結果を追加しています。Alpineでは56ページの翻訳、最終監査での欠落検出・修正、build、GitHub Actions deploy、公開サイトと複数カテゴリの代表ページ・asset確認まで完了しました。LivewireでもGitHub Actionsによるdeployを実施しました。

これはすべてのOSSで通用することが証明された完成済みフレームワークではありません。次のOSSへ適用できる、より成熟した標準ワークフロー候補です。

各作業では、次の3種類を分けます。

- **Common Core**: OSSが変わっても共通する責務。
- **Project Adapter**: 対象OSSごとに決める具体的方法・仕様。
- **保留**: 必要性や安全性がまだ十分に実証されていないもの。

## 1. 原文・公開構造を調査する

### Common Core

- upstreamの公式リポジトリ、ブランチ、原文ルートを特定する。
- 対象ページ、ファイル対応、ページ間リンク、navigationを調査する。
- 原文と日本語版の保存場所・相対関係を決める。
- 公開サイトの構造と、未翻訳ページの扱いを確認する。
- Markdown、コード、表、Callout、リンク、HTMLアンカーなどの構造を把握する。

### Project Adapter

- upstream repository / branch / source root
- 対象ページの発見方法と対象範囲
- 原文取得方法と保存場所
- URL、navigation、sidebarの対応
- HTMLアンカー、独自Markdown、コードフェンスの仕様
- 未翻訳ページへのリンク方針
- 実行デモを再現するかどうか
- build、deploy、公開確認の方法

ページ数だけで完了と判断しない。構造と情報量を確認できる単位を先に把握する。

## 2. upstreamを取得・同期する

### Common Core

- upstream原文をローカルで確認できる状態にする。
- 取得元、対象ブランチ、基準状態を記録する。
- ファイルの追加、削除、改名、移動を確認する。
- 同期後に日本語訳へ影響するページを特定する。
- どのupstream状態を比較基準としているか追跡可能にする。
- upstream原文だけの更新と、日本語訳の更新を分ける。

### Project Adapter

同期頻度、自動同期、変更PR、navigation変更、削除・改名の処理、基準位置の保存形式と更新条件を決める。基準位置が何を意味するか、いつ更新するか、翻訳完了やsnapshot取得・deployと連動するかはProject Adapterで定める。Common Coreでは、基準位置を比較基準の追跡情報として扱う。

## 3. AI実行ループ

AIは作業を単発で終了させず、次のループで継続する。

```text
選択 → 実行 → 検証 → 確定 → 次へ
```

### 選択

次のバッチを、repository、永続化された作業記録、rules、glossary、workflow document、upstream referenceから復元する。対象範囲、既存変更、前回の確定状態を確認する。

### 実行

Project Adapterの単位で翻訳、レビュー、必要なnavigation・index・README更新を行う。大きなページは見出しや意味単位に分割する。

### 検証

バッチの完了条件と停止条件を確認する。レビュー、`expected / reviewed / unreviewed`、構造・意味・リンク、build、diff check、永続化された状態を確認する。

### 確定

現在のバッチを、次回復元可能な永続チェックポイントとして確定する。Gitを使うプロジェクトではcommit / pushが実装例になる。チェックポイントは頻繁に作るが、チェックポイントを作ったこと自体を停止理由にしない。

### 次へ

停止条件に該当しなければ、正常に次のバッチへ進む。1バッチ、数ページ、数コミット、カテゴリの完了、区切りのよさだけでは停止しない。

### 継続条件

次を満たして安全に確定できた場合は、次のバッチへ進む。

- 対象作業が完了している。
- レビュー対象が確認済みである。
- `unreviewed = 0`である。
- Adapterで定めたbuild・diff checkが成功している。
- 確定済み状態が永続化され、次回そこから安全に復元可能である。

### 完了条件

各バッチの具体的な完了条件はProject Adapterで定める。Alpineで機能した例は、対象ページのレビュー完了、`unreviewed = 0`、build成功、diff check成功、commit / push済みである。これはGitを使う場合の実装例であり、全OSS共通の必須動作やコマンドを意味しない。

### 停止条件

AIだけで安全に継続できない場合は、現在バッチを可能な範囲で確定して停止する。

- 既存ルールでは判断できない新仕様。
- review未完了、または判断保留が残る。
- build、diff check、リンク、永続化や必要な状態管理の失敗。
- upstreamの重大変更、対象範囲の再定義、MVP方針との衝突。
- 認証、秘密情報、外部権限など人間判断が必要な状態。
- 実際のコンテキスト限界により、レビュー精度・指示保持・安全性が低下する状態。

### 停止閾値

停止条件を列挙するだけでは、AIが過度に保守的に停止する可能性がある。停止閾値を明示し、正常ならチェックポイントを通過して継続する。

Alpineでは、初期には数ページ・数バッチで安全側に停止する傾向があった。その後、「数バッチ完了は停止理由ではない」と明示し、新しいセッションへの切り替えも行った結果、21ページ・13コミットまで正常に継続し、実際に「これ以上継続するとレビュー精度と安全性を維持しにくい」と判断した地点で現在バッチをcleanに確定して停止できた。

ただし、21ページ・13コミットまで進めた原因が停止閾値の明示だけだったとは断定しない。新しいセッションへ切り替えた効果も含まれる可能性がある。

## 4. 翻訳する

### Common Core

- 原文を要約せず、情報量を維持する。
- 見出し、段落、リスト、表、コード、Callout、リンク、例を保持する。
- 条件、例外、制約、注意事項を省略しない。
- コードの実行構造と技術識別子を壊さない。
- 用語と表記をルール・glossaryに従って統一する。
- 新規ページとupstream差分更新の作業範囲を分ける。

### 新規ページ

```text
原文全体 → 構造把握 → 翻訳 → 全体レビュー → 人間確認 → build / 公開
```

### 既存ページのupstream更新

```text
upstream差分 → 影響範囲特定 → 局所更新 → 差分と前後文脈のレビュー → 人間確認 → build / 公開
```

変更行だけでなく、前後の条件・例外・制約、コードと説明の成立関係、周辺節・リンク・表・Calloutへの影響を確認する。

## 5. AIレビューと6ステップ

ページまたは差分ごとに、次の6ステップを維持する。

1. 原文の見出し、コード、リスト、blockquote、表、リンク、アンカーなどを列挙する。
2. 構造と情報量からレビュー単位を決める。
3. 単位ごとに翻訳・構造確認・意味確認を行う。
4. 各単位の完了状態を記録する。
5. `expected / reviewed / unreviewed`を照合する。
6. `unreviewed = 0`を確認してレビューCoverageを完了する。

レビュー単位は固定行数ではなく、見出し、段落、コード例、表、Calloutなどの意味のまとまりを基本にする。新規ページではページ全体、差分更新では変更箇所と影響する前後文脈を対象にする。

### `unreviewed = 0`の意味

`unreviewed = 0`は、設定したレビュー対象をすべてレビューしたことを示すCoverage完了条件である。

これは翻訳に欠落・誤訳が絶対にないことの証明ではない。

```text
Review Coverage complete ≠ Translation correctness/completeness guaranteed
```

Alpineでは、全56ページが存在し作業時点で`unreviewed = 0`としていたにもかかわらず、最終全体監査でMorph、Sort、Extending、Upgrade Guideなどの説明・表・コード例の欠落が見つかった。このため、ページ単位レビューとCompletion Gateを分離する。

## 6. 人間レビュー

AIレビューと人間レビューは別責務である。人間はAIの未解決事項、重要な条件・例外、コードと説明の対応、リンク・navigation・公開対象、代表ページの表示、明らかな欠落や誤訳を確認する。

人間が全ページを全文再レビューすることを一律の標準条件にはしない。必要な確認範囲と公開停止基準はProject Adapterで決める。判断保留を無理に完了扱いしない。

## 7. 最終全体監査（Completion Gate）

翻訳対象全体が揃った時点で、ページ単位レビューとは別に一度、プロジェクト全体の整合性を監査する。これは全ページをもう一度全文AIレビューする作業ではない。

### Common Core

- source / targetの対象ファイル対応を確認する。
- 未翻訳、追加、欠落、改名、移動を横断的に確認する。
- 明らかな見出し、説明、リスト、表、コード、Calloutの構造欠落を確認する。
- navigation、sidebar、index、READMEが実態と一致することを確認する。
- 内部リンクとアンカーを確認する。
- 未翻訳時だけ必要だった公式サイト退避リンクを確認する。
- 独自コードフェンス、意図しない実HTML、異常なアンカーなどを確認する。
- build、diff check、公開対象全体の整合性を確認する。

### Completion Gate

最終監査がPASSするまでdeploy工程へ進まない。問題が見つかれば修正して監査を繰り返す。構造数の一致は入口にすぎず、説明、条件、例外、コード例の明らかな欠落を内容として読む。

## 8. 翻訳完了とプロジェクト完了

### 翻訳完了

- 全翻訳対象ページが存在する。
- ページ単位レビューと人間確認が完了している。
- `unreviewed = 0`である。
- 最終全体監査（Completion Gate）がPASSしている。

### プロジェクト完了

翻訳完了に加えて、次を確認する。

- build成功。
- deploy成功。
- 公開URLが正常応答する。
- CSS、JavaScriptなどのassetが取得できる。
- navigationが利用できる。
- 異なるカテゴリの代表ページが通常のブラウザー相当で確認できる。
- READMEなどの公開案内が実際の公開状態と一致する。

翻訳ファイルを作っただけではプロジェクト完了とはしない。GitHub Actions、rsync、SSH、Secrets、server path、hosting providerなどの具体設定はProject Adapterに残す。

## 9. build・deploy・公開確認

build成功と、実際にユーザーがブラウザーで読めることを分ける。

```text
build → deploy → deployed site verification
```

### Common Core

- 公開URLが応答する。
- assetが壊れていない。
- navigationが利用できる。
- 異なる種類の代表ページを確認する。

ブラウザー自動化の具体的方法は共通仕様にしない。利用可能なら実ブラウザー相当で確認し、利用できなければHTTP status、HTML、asset、代表URLを確認する。

### Project Adapter

buildコマンド、出力パス、deploy workflow、認証・Secrets、remote path、host key、backup、公開URL、確認ページを定義する。`--delete`などの破壊的な同期は、対象ディレクトリが専用であることを確認した場合だけ使う。

## 10. upstream継続更新ループ

upstream更新にもAI実行ループを適用する。

```text
差分検出 → 影響範囲特定 → 局所翻訳 → review → 完了確認 → build / deploy → 次へ
```

新規翻訳ループと全く同一にする必要はない。Commonなのは差分、影響、レビュー、完了確認、公開確認という責務であり、具体的な同期方法・PR・基準位置更新はProject Adapterに残す。

差分更新では、変更行だけでなく前後の条件・例外・制約、コードと説明、周辺リンク・表・Calloutを確認する。基準位置の意味と更新条件はProject Adapterに従い、Common Coreでは比較基準を追跡可能な状態に保つ。

## 11. 状態のSSOTとチェックポイント

チャット履歴に依存せず、repository、永続化された作業記録、rules、glossary、workflow document、upstream referenceから次のセッションが作業状態を復元できるようにする。

review、build、永続化などで再開可能なチェックポイントを頻繁に作る。Gitを使う場合はcommit / pushがその実装例になる。ただし、安全なチェックポイント作成とチェックポイントごとの早期終了は同じではない。正常ならそのまま次のバッチへ進む。

## 12. 自動化と保留事項

自動化候補には、upstream差分取得、ファイル追加・削除・改名候補、構造数確認、リンク確認、build、diff check、deploy、公開成果物の疎通確認がある。ただし自動化の必要性と安全性を確認してから導入する。

次は今回の実証だけを理由に実装・標準化しない。

- 共通Review Skill
- 共通翻訳Skill
- AST、atomic claim、coverage unit、Coverage DB
- 翻訳管理DB
- 全OSS共通CI
- 自動意味完全性判定
- 全自動翻訳
- 自動的な人間レビュー範囲の決定

翻訳単位の判断、意味保持、条件・例外・制約、コードと説明の成立関係、対象外判断、OSS固有構造の解釈は、当面AIまたは人間の判断として残す。

## 13. 新しいOSSで始めるチェックリスト

- [ ] upstreamの正本、repository、branch、source rootを特定した。
- [ ] 対象範囲、発見方法、原文保存場所を決めた。
- [ ] upstream基準位置の記録方法と更新条件を決めた。
- [ ] navigation、URL、リンク方針を調査した。
- [ ] 独自Markdown、Callout、表、コードフェンス、アンカーを調査した。
- [ ] 実行デモの扱いを決めた。
- [ ] 翻訳しない識別子とコード内表示文字列の扱いを決めた。
- [ ] 翻訳ルールと用語集の最小版を作成した。
- [ ] build、deploy、公開確認方法を決めた。
- [ ] 代表的な1ページで最初のAI実行ループを実施した。
- [ ] 長く複雑なページでも6ステップを確認した。
- [ ] 新規翻訳と差分更新を少なくとも1件ずつ検証した。
- [ ] `expected / reviewed / unreviewed`を確認した。
- [ ] `unreviewed = 0`をCoverage完了として確認した。
- [ ] 全ページ完了後に最終全体監査を実施した。
- [ ] 翻訳完了とプロジェクト完了を別々に確認した。

小さいページだけで検証完了とはしない。短いページと複雑なページ、新規ページと差分更新、buildと公開確認の両方を確認する。

## v0.2の適用範囲

LivewireとAlpineの2例で、原文構造の列挙、意味単位のレビュー、差分と前後文脈の確認、`expected / reviewed / unreviewed`、最終全体監査、build、deploy、公開確認まで検証した。

この結果により、次のOSSへ適用できる候補としての成熟度は上がった。ただし、すべてのOSSにおける人間レビューの十分条件、Adapter項目の網羅性、自動化の適切な範囲はまだ仮説であり、次の実務で再評価する。

v0.1は履歴として保持する。v0.2は実証結果を反映した現在の標準ワークフロー候補である。
