# OSS公式ドキュメント日本語化 標準ワークフロー v0.1

## この文書の位置づけ

この手順は、OSS公式ドキュメントを日本語化するときに、人間とAIが同じ順序で作業するための実務手順です。

Livewire版とAlpine版で確認できた共通手順を基礎にしています。Alpine固有の仕様ではなく、3つ目以降のOSSで検証・更新する共通ワークフロー候補です。完成した汎用フレームワークではありません。

各フェーズでは、次の3種類を分けて扱います。

- **Common Core**: OSSが変わっても共通する作業。
- **Project Adapter**: 対象OSSごとに決める作業。
- **保留**: 必要性がまだ実証されていない作業。

---

## 1. 原文・公開構造を調査する

### 目的

翻訳を始める前に、何を正本とし、どの範囲を公開するかを確定する。

### Common Core

- upstreamの公式リポジトリ、ブランチ、原文ルートを特定する。
- 対象ページ、ページ間リンク、ナビゲーションを調査する。
- 原文と日本語版の保存場所・相対関係を決める。
- 公開サイトの構造と、未翻訳ページの扱いを確認する。
- Markdown、コード、表、リンクなど、ページを構成する要素を把握する。

### Project Adapterで決めること

- upstream repository / branch / source root
- 対象ページの発見方法
- 原文ファイルの保持場所
- URLとnavigationの対応
- HTMLアンカーの扱い
- 未翻訳ページへのリンク方針
- 独自Markdown、Callout、表、コードフェンスの仕様
- 実行デモを再現するかどうか

### 完了条件

- 原文の正本と対象範囲が説明できる。
- 公開対象と未翻訳範囲が確認できる。
- 代表ページの構造とリンク方針が確認できる。

### 注意点

ページ数だけで翻訳完了を判断しない。構造と情報量を確認できる単位を先に把握する。

## 2. upstreamを取得・同期する

### 目的

翻訳対象となる原文を取得し、どのupstream状態を基準にしているか追跡可能にする。

### Common Core

- upstream原文をローカルで確認できる状態にする。
- 取得元、取得日時、対象ブランチなどを確認できるようにする。
- 現在の原文と翻訳済み原文の基準状態を区別する。
- ファイルの追加、削除、改名、移動を確認する。
- 同期後に日本語訳へ影響するページを特定する。

### Project Adapterで決めること

- 原文取得方法（git、Raw URL、APIなど）
- 同期頻度と同期workflow
- ファイル追加・削除・改名の扱い
- navigation変更の扱い
- upstream基準位置の保存方法
- 基準位置をいつ更新するか

upstream基準位置は、どの状態を比較基準としたか追跡可能にする責務だけをCommon Coreとする。

特定のファイル名や、その値が示す具体的な意味は共通仕様にしない。基準位置の意味はProject Adapterで定義する。

### 完了条件

- 原文の取得元と基準状態が確認できる。
- 同期によるファイル差分が確認できる。
- 翻訳対象ページへの影響範囲が特定できる。

### 注意点

upstream原文だけを更新する同期と、日本語訳を更新する作業を混同しない。基準位置の更新条件も先に決める。

## 3. 翻訳する

### 目的

原文の情報、構造、技術的意味を保った日本語版を作成する。

### Common Core

- 原文を要約せず、情報量を維持する。
- 見出し、段落、リスト、表、コード、Callout、リンク、例を保持する。
- 条件、例外、制約、注意事項を省略しない。
- コードの実行構造と技術識別子を壊さない。
- 用語と表記を翻訳ルールに従って統一する。
- 新規ページと差分更新で作業範囲を分ける。

### Project Adapterで決めること

- 翻訳ルールと用語集
- 翻訳しない識別子
- コード内の表示文字列を翻訳する範囲
- 独自コードフェンスとCalloutの扱い
- 実行デモを再現するかどうか
- HTMLアンカーとリンク先の変換
- 未翻訳ページへのリンク方針
- OSS固有のローカライズ方針

### 新規ページ

原文全体を対象にする。

```text
原文全体
→ 構造を把握
→ 翻訳
→ 全体レビュー
→ 人間確認
→ build / 公開
```

### 既存ページのupstream更新

全文再翻訳を標準動作にしない。

```text
upstream差分
→ 影響範囲特定
→ 既存訳を保持して局所更新
→ 差分と前後文脈をレビュー
→ 人間確認
→ build / 公開
```

差分更新では変更行だけでなく、前後の条件、例外と制約、関連する説明、コードと説明の成立関係、周辺節・リンク・表・Calloutへの影響を確認する。

### 完了条件

- 翻訳対象の構造要素が対応している。
- 原文の意味と情報量が保たれている。
- 翻訳ルール、用語、リンク方針に適合している。
- AIレビューと人間確認へ進める状態になっている。

## 4. AIレビューを行う

### 目的

翻訳の構造的欠落、意味的欠落、技術的な不整合を体系的に確認する。

### Common Core

AIレビューでは、少なくとも次を確認する。

- 構造的欠落
- 意味的欠落
- 条件、例外、制約
- コードと説明の対応
- リンクとアンカー
- 周辺節との整合
- OSS固有構造の保持

### Project Adapterで決めること

次をレビュー対象へ変換する方法を定義する。

- Callout / blockquote
- 表の列、行、セル
- 独自コードフェンス
- 実行デモ
- HTMLアンカー
- 独自注釈記法
- 翻訳しない識別子
- 未翻訳ページへのリンク

### 標準AIレビュー手順

1. 原文構造を列挙する。
2. レビュー単位を決める。
3. 単位ごとに翻訳・構造確認・意味確認を行う。
4. 単位ごとの完了状態を記録する。
5. `expected / reviewed / unreviewed`を照合する。
6. `unreviewed = 0`を確認して完了とする。

レビュー単位は固定行数ではなく、見出し、段落、コード例、表、Calloutなどの意味のまとまりを基本にする。新規ページではページ全体を対象にし、差分更新では変更箇所と影響する前後の文脈を対象にする。

### 最小レビュー記録

```text
対象ページ / 差分:
レビュー単位:
- [ ] Unit 1:
- [ ] Unit 2:

expected:
reviewed:
unreviewed:

対象外:
発見・修正事項:
最終判定: complete / incomplete
```

この記録をGitへ恒久保存することは、v0.1の標準ルールにしない。

### 完了条件

- すべてのレビュー単位が完了または対象外として記録されている。
- `expected`、`reviewed`、`unreviewed`が一致している。
- `unreviewed = 0`である。
- 未解決の判断保留事項が人間レビューへ引き継がれている。

## 5. 人間レビューを行う

### 目的

AIだけでは確定できない判断、公開上のリスク、翻訳方針との適合を確認する。

### 実証済みの範囲

- AIレビューと人間レビューは別責務である。
- AIが未解決・判断保留した点は人間が確認する。
- build成功だけでは翻訳品質や情報完全性を保証できない。

### 現時点の推奨

人間レビューでは、少なくとも次を確認する。

- AIレビューの未解決事項
- 条件、例外、技術的意味が重要な箇所
- コードと説明の対応
- リンク、navigation、公開対象
- 代表的なページの表示結果
- 公開に影響する明らかな欠落や誤訳

「人間が必ず全ページを全文再レビューする」とは、現時点では標準条件にしない。AIレビュー結果をどこまで前提にできるかも、OSSとリスクに応じて判断する。

### Project Adapterで決めること

- 必須の人間確認範囲
- リリース前に確認する代表ページ
- 技術担当者やネイティブレビュアーの関与方法
- 公開停止が必要な問題の基準

### 完了条件

- 人間確認が必要な事項の判断が完了している。
- 公開を止める問題が残っていない。
- 判断保留を無理に自動完了扱いしていない。

## 6. build・公開する

### 目的

翻訳を公開可能な成果物に変換し、公開前後の破損を確認する。

### Common Core

- buildを実行する。
- Markdown、リンク、コード、navigationの破損を確認する。
- 意図しない差分やファイル変更を確認する。
- 公開成果物が想定URLで表示されることを確認する。
- AIレビューとbuild成功を別の確認結果として扱う。

### Project Adapterで決めること

- buildコマンド
- 静的サイト設定
- リンクチェック方法
- deploy workflow
- deploy先、認証、秘密情報
- 公開後の確認URLと確認範囲

### 完了条件

- buildが成功している。
- リンクとnavigationに重大な問題がない。
- 公開成果物を確認できる。
- 公開前後に対象外の変更がない。

## 7. upstream更新へ継続対応する

### 目的

upstreamの更新を検知し、既存の日本語訳へ必要な変更だけを安全に反映する。

### Common Core

- 新旧upstreamの差分を確認する。
- 変更ファイルと影響ページを特定する。
- 追加、削除、改名、移動を確認する。
- 変更箇所と前後文脈をレビューする。
- 翻訳、AIレビュー、人間確認、buildを必要な範囲で繰り返す。
- upstream基準位置をAdapterのルールに従って更新する。

### Project Adapterで決めること

- 同期頻度
- 自動同期の方法
- 変更PRの作り方
- 削除・改名・navigation変更の処理
- 翻訳未完了時の基準位置更新条件
- upstream変更を公開へ反映する順序

### 完了条件

- upstream差分の影響範囲が確認できる。
- 必要な日本語訳が更新されている。
- `unreviewed = 0`になっている。
- buildと公開確認が完了している。
- Adapterで定めた基準位置が適切に更新されている。

## 自動化の扱い

現時点で自動化しやすい候補には、upstream差分取得、ファイル追加・削除・改名候補の検知、見出し・コード・表・Calloutなどの構造数確認、リンク確認、build、diff check、deploy、公開成果物の疎通確認がある。

ただし、自動化対象をこれらに限定しない。必要性と安全性を確認してから導入する。

現時点では、翻訳単位の判断、意味保持、条件・例外・制約の確認、コードと説明の成立関係、対象外判断、OSS固有構造の解釈はAIまたは人間の判断として残す。

## v0.1で保留するもの

以下は不要と断定せず、必要性がまだ実証されていないため保留する。

- 共通Review Skill
- 共通翻訳Skill
- Coverage履歴の恒久保存
- ASTベースのチェッカー
- atomic claim
- coverage unit
- 自動意味完全性判定
- 翻訳管理DB
- 全OSS共通CI
- 全自動翻訳
- 自動的な人間レビュー範囲の決定

3つ目のOSSで同じ手順を実際に使い、繰り返し発生する負担や判断の揺れが確認できた時点で再評価する。

## 新しいOSSで始めるときのチェックリスト

- [ ] upstreamの正本を特定した。
- [ ] repository、branch、source rootを特定した。
- [ ] 原文の対象範囲と発見方法を決めた。
- [ ] 原文取得方法を決めた。
- [ ] upstream基準位置の記録方法を決めた。
- [ ] navigation、URL、リンク方針を調査した。
- [ ] 独自Markdown、Callout、表、コードフェンスを調査した。
- [ ] 実行デモとHTMLアンカーの扱いを決めた。
- [ ] 翻訳しない識別子とコード内表示文字列の扱いを決めた。
- [ ] 翻訳ルールと用語集の最小版を作成した。
- [ ] build、deploy、公開確認方法を決めた。
- [ ] 代表的な1ページで最初の1ループを実施した。
- [ ] 長め・複雑なページでも6ステップを確認した。
- [ ] upstream差分更新を、実差分または過去差分のdry-runで1件検証した。
- [ ] `expected / reviewed / unreviewed`を確認した。
- [ ] `unreviewed = 0`で完了した。

小さいページだけで検証完了とはしない。新規ページと差分更新、短いページと複雑なページの両方を確認する。

## v0.1の適用範囲

この手順は、3つ目のOSSへ持ち込んで検証できる状態にある。

実証済みなのは、原文構造の列挙、意味単位のレビュー、差分と前後文脈の確認、構造要素の照合、`expected / reviewed / unreviewed`による完了確認である。

一方、人間レビューの十分条件、Adapter項目の網羅性、自動化の適切な範囲はまだ仮説である。

したがって、この文書を完成した汎用フレームワークとは扱わず、3つ目のOSSで実務に使い、必要な箇所だけ更新する。
